# Section 3 技術邊界原則 (Technical Boundary Principles)

## 核心原則

**Section 3 是 PM-to-Engineering 溝通橋樑，不是實作規格書。**

PRD 應該回答：
- ✅ **做什麼 (What)** — 業務需求與預期效果
- ✅ **為什麼 (Why)** — 業務價值與決策依據
- ⚠️ **怎麼做 (How)** — 僅限業務邏輯 How，避免技術實作 How

---

## 判斷標準：什麼該寫，什麼不該寫

### 三個關鍵問題

| 問題 | 如果答案是… | 處理方式 |
|------|------------|---------|
| 1. 這個 How 影響**用戶體驗**嗎？ | ✅ 是 | **保留** |
| 2. 這個 How 是**唯一可行**的方案嗎？ | ❌ 否 | **刪除**，改為效果描述 |
| 3. 工程師**不知道這個 How**會做錯嗎？ | ✅ 是 | **保留** |

### 簡化判斷法

**如果可以用其他技術方案達成同樣效果 → 這是 Technical How → 刪除**

### 應該保留的 How（Business How）

#### ✅ 1. 用戶操作流程
**特徵**：描述用戶完成任務的步驟與路徑
- 主要流程、替代路徑、異常路徑
- 工作流斷點（用戶可以在哪裡進入/離開系統）
- 跨角色協作流程

**範例**：
```markdown
✓ "用戶可選擇上傳文件或手動填寫表單"
✓ "審核者退回時，系統引導用戶建立修改版本"
✓ "用戶可在任何階段儲存草稿或直接送出"
```

#### ✅ 2. 業務規則
**特徵**：業務邏輯的運作方式，不遵守會產生錯誤結果
- 狀態轉換規則
- 編號/版本分配規則
- 計算公式、優先級規則
- 權限判斷條件

**範例**：
```markdown
✓ "版本號遞增：Major 更新 X 並重置 Y/Z 為 0"
✓ "訂單編號每個租戶獨立計算"
✓ "狀態轉換：draft → submitted → approved"
✓ "同一資源只能有一個 active 狀態的版本"
```

#### ✅ 3. 異常處理與邊界條件
**特徵**：產品在非預期情境下的行為
- 用戶取消操作時的處理（Reverse Flow）
- 錯誤輸入的處理（Error Handling）
- 外部服務失敗時的降級方案
- 衝突解決策略

**範例**：
```markdown
✓ "上傳失敗時保留已填寫內容，允許用戶重試"
✓ "多人同時編輯時，後儲存者收到衝突提示"
✓ "AI 解析失敗時，fallback 到手動填寫流程"
```

### 應該刪除/簡化的 How（Technical How）

#### ❌ 1. 技術實現方案
**特徵**：指定具體技術、演算法、架構模式

**常見陷阱**：
- 鎖機制：心跳鎖、樂觀鎖、悲觀鎖、分布式鎖
- 快取策略：Redis、Memcached、CDN
- 認證方式：OAuth、JWT、Session
- 儲存方式：base64、object storage、blob

**修正方式**：改為效果描述
```diff
- ❌ "採獨占編輯（心跳鎖），每 30 秒發送 heartbeat"
+ ✅ "同一時間僅允許一位使用者編輯"

- ❌ "採樂觀鎖（Optimistic Lock），基於 version 欄位"
+ ✅ "支援多人編輯，衝突時提示使用者重新載入"

- ❌ "使用 Redis 快取清單資料"
+ ✅ "清單需快速載入（目標 < 1 秒）"
```

#### ❌ 2. 精確性能指標
**特徵**：毫秒級數字、百分位數 (p95/p99)、具體 TPS/QPS

**修正方式**：給範圍 + 註記交由工程定義
```diff
- ❌ "API 回應時間 < 200ms (p99)"
+ ✅ "API 需快速回應（目標 < 500ms）"

- ❌ "清單頁載入延遲 < 500ms"
+ ✅ "清單頁需快速載入（目標 < 1 秒）"

- ❌ "批次匯出（50 筆）< 15 秒"
+ ✅ "批次匯出需在短時間內完成，顯示進度"

+ ✅ 加註：「※ 具體性能指標由技術團隊依系統架構制定」
```

#### ❌ 3. 詳細資料結構
**特徵**：列出所有欄位、型別、巢狀層級、關聯表

**修正方式**：僅概念層級 + 註記交由 API Spec
```diff
- ❌ 列出完整欄位樹狀結構：
  DecisionRecord
  ├── id (UUID)
  ├── title (string, max 200)
  ├── status (enum: draft|committed)
  ├── metadata
  │   ├── createdAt (timestamp)
  │   └── createdBy (User FK)

+ ✅ 概念層級描述：
  **核心實體**：
  - 基本識別：ID、標題、狀態
  - 內容：業務欄位 A、B、C
  - 關聯：關聯實體 X、Y
  
  ※ 詳細資料結構由 API Spec 與 Schema 定義
```

#### ❌ 4. 技術術語
**特徵**：database 用詞、程式語言概念、系統內部狀態

**修正方式**：改為業務語言
```diff
- ❌ "時間戳 (timestamp)"
+ ✅ "時間"

- ❌ "欄位值為 null"
+ ✅ "欄位空白" 或用業務術語描述狀態

- ❌ "原子寫入、重試佇列"
+ ✅ "確保資料一致性" 或 "具體可靠性機制由工程團隊決定"

- ❌ "信心度 0–1 浮點數，閾值 < 0.5 / 0.5–0.8 / ≥ 0.8"
+ ✅ "信心度分為低/中/高三級"
```

## Section 3 常見模式索引

### 模式 1：資源鎖定與並發控制
**識別特徵**：多個用戶可能同時編輯同一資源

**Business How（保留）**：
- 同一時間可以有幾人編輯？（獨占 vs 多人）
- 衝突時如何通知用戶？（提示訊息內容）
- 是否自動合併？（用戶決定 vs 系統處理）

**Technical How（移除）**：
- ❌ 心跳鎖、樂觀鎖、悲觀鎖、分布式鎖
- ❌ version 欄位、ETag、CAS 操作

---

### 模式 2：性能與效能要求
**識別特徵**：回應時間、吞吐量、資料量限制

**Business How（保留）**：
- 用戶期待的回應速度（快速 / 即時 / 合理等待）
- 超時時的用戶體驗（顯示進度 / 允許取消 / 降級方案）
- 資料量限制的業務原因（檔案大小上限 / 批次處理數量）

**Technical How（移除）**：
- ❌ 精確毫秒數（< 200ms、< 500ms）
- ❌ 百分位數（p95、p99）
- ❌ TPS、QPS、併發數

**修正方式**：給範圍 + 註記
```markdown
✓ "需快速回應（目標 < 1 秒）"
✓ "※ 具體性能指標由技術團隊依系統架構制定"
```

---

### 模式 3：實體與資料模型
**識別特徵**：需要描述系統核心實體與關係

**Business How（保留）**：
- 實體概念與業務意義
- 實體間關係（一對一 / 一對多 / 多對多）
- 核心屬性的業務語意
- 生命週期狀態（draft / active / archived）

**Technical How（移除）**：
- ❌ 完整欄位清單與型別（id: UUID, title: string(200)）
- ❌ 索引、外鍵、巢狀結構
- ❌ 資料庫正規化設計

**修正方式**：概念層級 + 註記
```markdown
> **⚠️ 概念模型**：以下為概念層級，非工程實作規格
> **※ 詳細資料結構由 API Spec 與 Schema 定義**

**核心實體名稱**：
- 基本識別：ID、名稱、狀態
- 業務內容：欄位 A、欄位 B
- 關聯：關聯實體 X（一對多）
```

---

### 模式 4：審計與軌跡記錄
**識別特徵**：需要記錄「誰在何時做了什麼」

**Business How（保留）**：
- 需要記錄哪些操作類型？（建立 / 修改 / 刪除 / 狀態變更）
- 記錄的保留規則？（不可刪除 / 保留 N 天 / 可匯出）
- 用戶可查看哪些軌跡？（自己的 vs 全部）

**Technical How（移除）**：
- ❌ timestamp 欄位、createdAt / updatedAt
- ❌ 審計表 schema、trigger 設計

**修正方式**：
```diff
- ❌ "記錄時間戳與操作人"
+ ✅ "記錄操作人、時間與操作內容"

- ❌ "使用 audit_log 表，含 user_id、action_type、timestamp"
+ ✅ "系統需記錄關鍵操作軌跡"
```

---

### 模式 5：外部整合與失敗處理
**識別特徵**：依賴外部服務或第三方 API

**Business How（保留）**：
- 整合失敗時的用戶體驗？（重試 / 降級方案 / 錯誤提示）
- 資料同步的業務規則？（即時 / 批次 / 最終一致性）
- 斷線後的恢復行為？（保留草稿 / 自動重試 / 用戶手動觸發）

**Technical How（移除）**：
- ❌ 原子寫入、兩階段提交、Saga 模式
- ❌ 重試佇列、訊息中介軟體、補償事務

**修正方式**：
```diff
- ❌ "Phase 3 可靠性機制（原子寫入、重試佇列）由工程團隊決定"
+ ✅ "具體可靠性機制由工程團隊依系統架構決定"

- ❌ "使用 message queue 確保最終一致性"
+ ✅ "資料需保持一致性，同步失敗時允許用戶重試"
```

## Section 3 寫作檢查清單

在完成 Section 3 後，執行以下檢查：

### 技術細節自檢

- [ ] **技術術語檢查**：搜尋「時間戳、原子、重試、佇列、cache、lock、heartbeat、樂觀鎖、悲觀鎖」
  - 若出現，改為業務語言或移除

- [ ] **性能數字檢查**：搜尋「< [數字]ms、< [數字]秒」
  - 若出現精確數字，改為範圍描述（目標 < X）+ 註記「具體指標由技術團隊制定」

- [ ] **資料模型檢查**：確認是否列出詳細欄位/型別/嵌套結構
  - 若是，簡化為概念層級 + 新增「詳細資料結構由 API Spec 定義」

- [ ] **實現方案檢查**：確認是否指定具體技術方案（如 Redis、OAuth、JWT）
  - 若是，改為效果描述或能力描述

### 業務邏輯完整性檢查

- [ ] **用戶操作流程**：核心路徑、替代路徑、異常路徑是否完整？
- [ ] **業務規則**：狀態轉換、編號分配、版本遞增規則是否明確？
- [ ] **異常處理**：所有 AC 的 Reverse Flow 與 Error Handling 是否定義？
- [ ] **權限規則**：RBAC 矩陣是否完整？

---

## 總結：Business How vs Technical How

| 類型 | 是否保留 | 原因 | 判斷關鍵 |
|------|---------|------|---------|
| 用戶操作流程 | ✅ 保留 | PRD 核心 | 影響用戶體驗 |
| 業務規則 | ✅ 保留 | 驗收依據 | 不知道會做錯 |
| 異常處理邏輯 | ✅ 保留 | 產品完整性 | 影響用戶體驗 |
| 技術實現方案 | ❌ 刪除 | 限制技術選型 | 可用其他方案 |
| 精確性能數字 | ⚠️ 簡化 | SLA 職責 | 給 range 即可 |
| 詳細數據結構 | ❌ 刪除 | API Spec 職責 | 實作細節 |
| 技術術語 | ❌ 簡化 | 溝通障礙 | 改用業務語言 |
