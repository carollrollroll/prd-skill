# Section 3 技術邊界原則 (Technical Boundary Principles)

## 核心原則

**Section 3 是 PM-to-Engineering 溝通橋樑，不是實作規格書。**

PRD 應該回答：
- ✅ **做什麼 (What)** — 業務需求與預期效果
- ✅ **為什麼 (Why)** — 業務價值與決策依據
- ⚠️ **怎麼做 (How)** — 僅限業務邏輯 How，避免技術實作 How

---

## 判斷標準：什麼該寫，什麼不該寫

### 問自己三個問題

| 問題 | 如果答案是… | 處理方式 |
|------|------------|---------|
| 1. 這個 How 影響**用戶體驗**嗎？ | ✅ 是 | **保留** |
| 2. 這個 How 是**唯一可行**的方案嗎？ | ❌ 否 | **刪除**，改為效果描述 |
| 3. 工程師**不知道這個 How**會做錯嗎？ | ✅ 是 | **保留** |

### 應該保留的 How（Business How）

#### ✅ 1. 用戶操作流程的 How
```markdown
例：路徑 A～E、工作流斷點設計
→ 這是"用戶如何完成任務"，屬於產品設計核心
```

#### ✅ 2. 業務規則的 How
```markdown
例：
- 版本號如何遞增 (Major更新X並重置Y/Z)
- 訂單編號如何分配 (每個租戶獨立計算)
- 狀態如何轉換 (draft → submitted → approved → rejected)
→ 這是"業務邏輯如何運作"，必須在PRD定義
```

#### ✅ 3. 異常處理的 How
```markdown
例：
- 審核退回時如何處理 (建立副本，沿用原ID)
- AI解析失敗時如何處理 (fallback到手動輸入)
→ 這是"產品行為如何應對edge case"
```

### 應該刪除/簡化的 How（Technical How）

#### ❌ 1. 技術實現方案
```diff
- ❌ "採獨占編輯（心跳鎖）"
+ ✅ "同一時間僅允許一位使用者編輯"

- ❌ "採樂觀鎖（Optimistic Lock）"  
+ ✅ "支援多人編輯，衝突時提示使用者"
```

**原因**：工程師可能用其他技術達成同樣效果。

#### ❌ 2. 性能指標數字
```diff
- ❌ "API 回應時間 < 200ms (p99)"
+ ✅ "API 需快速回應（目標 < 500ms）"

- ❌ "AI 解析回應時間 < 30 秒"
+ ✅ "AI 解析需在合理時間內完成（目標 < 30 秒），超時顯示進度"
```

**原因**：具體數字應該在 SLA/NFR 文檔中，PRD 給 range 即可。

#### ❌ 3. 數據結構細節
```diff
- ❌ 列出所有欄位、嵌套層級、型別定義
+ ✅ 只寫實體關係與核心屬性
```

**原因**：這是 API Spec / Schema 的職責。

#### ❌ 4. 技術術語
```diff
- ❌ "信心度（confidence: 0–1）分三級（低 < 0.5 / 中 0.5–0.8 / 高 ≥ 0.8）"
+ ✅ "信心度分為低/中/高三級，具體閾值由技術團隊依 AI 模型特性決定"

- ❌ "CAB ID 永遠為 null"
+ ✅ "不經 CAB 流程"

- ❌ "時間戳 (timestamp)"
+ ✅ "時間"
```

**原因**：避免用技術術語，改用業務語言。

## 常見技術細節陷阱與修正範例

### 1. §非功能需求(NFR)

#### ❌ 過於技術
```markdown
### 非功能需求(NFR)
- 清單頁載入延遲 < 500ms（含搜尋/篩選）
- 圖片上傳單檔上限 5MB；嵌入需在 3 秒內完成解析
- AI 解析回應時間 < 30 秒
- 批次匯出（zip，50 筆以內）< 15 秒
```

#### ✅ 業務導向
```markdown
### 非功能需求(NFR)

**效能要求**：
- 清單頁需快速載入並支援流暢的搜尋/篩選（目標 < 1 秒）
- AI 解析需在合理時間內完成（目標 < 30 秒），超時顯示進度提示
- 批次匯出需在短時間內完成，顯示進度

**檔案限制**：
- 圖片上傳單檔上限 5MB
- 上傳文件大小上限：Markdown 10MB、PDF 20MB

※ 具體性能指標由技術團隊依系統架構與使用者體驗要求制定
```

### 2. §並發編輯處理策略

#### ❌ 過於技術
```markdown
### 並發編輯處理策略
- **畫布編輯**：採**獨占編輯（心跳鎖）**，每30秒發送heartbeat
- **表單編輯**：採**樂觀鎖（Optimistic Lock）**，基於version欄位
```

#### ✅ 業務導向
```markdown
### 並發編輯處理策略
- **畫布編輯**：同一時間僅允許一位使用者編輯
- **表單編輯**：支援多人同時編輯。當發生衝突時（後儲存者的編輯基於已過時的版本），系統提示「⚠️ 此資料已被其他人修改，請重新載入後再編輯」
- **不做自動合併**：由使用者決定保留哪個版本
```

### 3. §核心資料模型

#### ❌ 過於技術
```markdown
### 核心資料模型

```
DecisionRecord
├── id                                    (內部資料 ID)
├── adrNumber                             (ADR 編號)
├── title
├── status: draft | committed | deprecated
├── cabId                                 (關聯的 CAB case ID)
├── currentVersion                        (目前版本號)
├── date
├── author
├── tags                                  (標籤清單)
├── basicInfo
│   ├── requirementType: new_requirement | system_optimization
│   ├── targetUser                        (WHO)
│   ├── requirementSummary                (WHY)
│   ├── decisionSummary                   (WHAT)
│   └── consequence
├── domains                               (三面向)
│   ├── business
│   │   └── diagrams
│   │       ├── id, type: image | drawio
│   │       └── fileReference
```
```

#### ✅ 業務導向
```markdown
### 核心資料模型

> **⚠️ 概念模型**：以下為 PM 端的概念模型，說明實體關係與核心屬性，非工程實作規格。
> 
> **※ 詳細資料結構由 API Spec 與 Schema 定義**

#### DecisionRecord (ADR 記錄)

**基本識別**：
- ADR 編號、標題、狀態（draft/committed/deprecated）
- 當前版本號（語意化版本 X.Y.Z）、建立/更新時間、作者

**內容**：
- 基本資訊：需求類型、Who/Why/What/Consequence、標籤
- 來源標記：manual | ai_import | design_studio

**架構設計**：
- 三面向（業務/應用/基礎設施）架構圖集合
- 每個面向包含：圖片架構圖、draw.io 圖表

**關聯**：
- CAB case ID、原始匯入文件、複製來源 ADR ID

**歷程**：
- 版本歷史：版本號、變更摘要、變更類型、內容快照
```

### 4. §軌跡記錄(Audit Trail)

#### ❌ 過於技術
```markdown
### 軌跡記錄(Audit Trail)
- ADR 建立、複製、刪除、狀態變更等關鍵事件皆需記錄時間戳與操作人
- 設計歷程保存每個版本的完整快照，不可刪除或覆寫
- 匯入匯出操作需留痕（記錄操作人、時間、檔案名稱）
- AI 匯入需額外記錄信心度分數
```

#### ✅ 業務導向
```markdown
### 軌跡記錄(Audit Trail)
- 系統需記錄關鍵操作的軌跡，包含操作人、時間與操作內容
- 具體記錄項目包含：建立、複製、刪除、狀態變更、匯入匯出操作
- 設計歷程保存每個版本的完整快照，不可刪除或覆寫
- AI 匯入需額外記錄解析信心度資訊
```

### 5. §系統邊界/相依與整合

#### ❌ 過於技術
```markdown
**失敗處理**：送審途中斷線時 `cabId` 未寫入，ADR 維持 `draft`。
Phase 3 可靠性機制（原子寫入、重試佇列）由工程團隊依架構決定。
```

#### ✅ 業務導向
```markdown
**失敗處理**：送審途中斷線時，ADR 維持 `draft` 狀態，用戶可重試。
具體可靠性機制由工程團隊依系統架構決定。
```

## Section 3 寫作檢查清單

在完成 Section 3 後，執行以下檢查：

### 技術細節自檢

- [ ] **技術術語檢查**：搜尋「時間戳、原子、重試、佇列、cache、lock、heartbeat、樂觀鎖、悲觀鎖」
  - 若出現，改為業務語言或移除

- [ ] **性能數字檢查**：搜尋「< [數字]ms、< [數字]秒」
  - 若出現精確數字，改為範圍描述（目標 < X）+ 註記「具體指標由技術團隊制定」

- [ ] **資料模型檢查**：確認是否列出詳細欄位/型別/嵌套結構
  - 若是，簡化為概念層級 + 新增「詳細資料結構由 API Spec 定義」

- [ ] **實現方案檢查**：確認是否指定具體技術方案（如 Redis、OAuth、JWT）
  - 若是，改為效果描述或能力描述

### 業務邏輯完整性檢查

- [ ] **用戶操作流程**：核心路徑、替代路徑、異常路徑是否完整？
- [ ] **業務規則**：狀態轉換、編號分配、版本遞增規則是否明確？
- [ ] **異常處理**：所有 AC 的 Reverse Flow 與 Error Handling 是否定義？
- [ ] **權限規則**：RBAC 矩陣是否完整？

## 總結：Business How vs Technical How

| 類型 | 是否保留 | 原因 | 判斷關鍵 |
|------|---------|------|---------|
| 用戶操作流程 | ✅ 保留 | PRD 核心 | 影響用戶體驗 |
| 業務規則 | ✅ 保留 | 驗收依據 | 不知道會做錯 |
| 異常處理邏輯 | ✅ 保留 | 產品完整性 | 影響用戶體驗 |
| 技術實現方案 | ❌ 刪除 | 限制技術選型 | 可用其他方案 |
| 精確性能數字 | ⚠️ 簡化 | SLA 職責 | 給 range 即可 |
| 詳細數據結構 | ❌ 刪除 | API Spec 職責 | 實作細節 |
| 技術術語 | ❌ 簡化 | 溝通障礙 | 改用業務語言 |
