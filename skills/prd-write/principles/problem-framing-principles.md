# Problem Framing Principles

Use this reference when drafting `Section 1.1 問題與情境 Context`.

## 1. Core Mindset

Section 1.1 is not background. It is the argument for why this problem deserves to be solved now, by us.

Every field must answer a skeptic, not describe a situation.

## 2. As-Is / To-Be Rule

`As-Is` describes the user's current workaround and what breaks about it — not the absence of your feature.

`To-Be` describes the experience after the solution ships — not a list of capabilities.

Both must be concrete enough that a reader who has never seen your product can visualize the before and after.

- Bad As-Is: "Users cannot export reports."
- Good As-Is: "Users copy data into Excel manually every week, then re-format it before sharing — errors are common and the process takes 2–3 hours."
- Bad To-Be: "Users will be able to export reports in one click."
- Good To-Be: "Users schedule a report once; it arrives in their inbox formatted and ready to share — no manual steps."

## 3. Why Now Rule

`Market Trend / Why Now?` must identify a specific change — in regulation, technology, user behavior, or competitive landscape — that makes this the right moment.

"Users have always wanted this" is not a Why Now. Identify what shifted.

- Acceptable triggers: a regulatory deadline, a shift in user expectations driven by a competitor, a new technical capability that removes a previous constraint, a macro trend that changed user context.
- If no credible trigger exists, the timing assumption is weak. Surface that explicitly rather than omitting it.

## 4. Value Proposition Rule

`Value Proposition / Why Us?` must make a defensible differentiation claim — not a feature list.

Ask: if a competitor built the same feature, would this claim still be true? If yes, it is not a differentiation. Find what is unique to your position, data, relationships, or product context.

- Focus on structural advantages: existing user base, proprietary data, integration depth, domain expertise, switching cost already built up.
- One strong claim is better than three weak ones.

## 5. Scope Boundary

Section 1.1 covers problem context and market positioning only.

- Business model, pricing, and monetization belong in `Section 1.3`.
- User requirements and jobs-to-be-done belong in `Section 1.2`.
- Do not conflate market opportunity size with a business value argument.

## 6. Common Anti-Patterns

- Writing As-Is as "the system currently lacks X" instead of describing the user's actual workaround.
- Writing To-Be as a feature spec instead of an outcome description.
- Using generic market growth stats as a substitute for a Why Now argument.
- Listing multiple value propositions without ranking or committing to one primary differentiator.
- Describing an internal pain point as if it were a user problem.
